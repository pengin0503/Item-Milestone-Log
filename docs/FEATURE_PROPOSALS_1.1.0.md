### P15. 持ち運べる収納の中身も数える（opt-in）

**目的と根拠**
- Mod パックでは素材をバックパックやシュルカーボックスに入れて持ち歩くことが多く、数量ターゲット（例: ダイヤ ×1000）は「インベントリに同時に持つ」では達成しにくい

**仕様案**
- Config `countContainerContents`（boolean、既定 false）。true のとき、所持数にインベントリ内の収納アイテムの中身を加える: バニラのコンテナ（シュルカーボックスの内容）、バンドルの内容、NeoForge のアイテムのハンドラ（バックパックなど）。入れ子は1段まで
- 判定・進捗（Q9 / F1）・記録の確定のすべてに適用する

**コスト・リスク**: 中〜大。
- **1.0.1 の決定を覆す**（`QUANTITY_SPEC_1.0.1.md` Q2 と FEATURE_SPEC_1.0.1 F14 で「シュルカーボックスの中身・他 Mod のストレージは数えない」と決めている）
- スキャンのたびに収納の中身を読むため、負荷が増える（大きなバックパックを多く持つ場合）
- バックパックによっては中身をワールド側に持ち、ハンドラの取得でデータを読み込むものがある（Mod ごとの挙動の確認が要る）

**推奨度**: 要判断（採用するなら 1.1.0 ではなく、実際の Mod パックでの検証を前提に後の版を勧める）

### P16. 世界初・制覇のタイトル演出

**目的と根拠**
- 世界初やプリセット制覇はチャットの1行で流れてしまい、特別さが伝わりにくい

**仕様案**

**コスト・リスク**: 小。ただし世界初については F7（`title %player% ...`）でも実現できるので重複がある。

**推奨度**: 低

### P33. Discord の Webhook URL を設定ファイルに書かずに済むようにする

**目的と根拠**
- `discordWebhookUrl` は設定ファイル（`config/itemmilestonelog-common.toml`、26.3 は `itemmilestonelog-local.toml`）に平文で書かれる。Webhook の URL を知っている人は誰でもそのチャンネルに投稿できる（コードはこの URL を秘密として扱い、ログやチャットに出さない。`DiscordNotifier` の Javadoc）
- シングルプレイでは、この設定ファイルは全ワールドで共通（仕様書の制約8・X1）。あるワールドのために設定した Webhook に、別のワールドの記録も投稿される
- Mod パックの製作者が、自分のインスタンスの config フォルダを含めてパックを書き出すと、URL も配られる。受け取った全員のシングルプレイの記録が、製作者のチャンネルに投稿される

**仕様案**
- `discordWebhookUrl` に `env:<変数名>`（例 `env:IML_DISCORD_WEBHOOK`）と書いたら、その環境変数の値を URL として使う。変数が無い・空なら無効（従来の空と同じ）。値は設定ファイルにも、ログにも残らない。ホスティングの管理画面で環境変数を設定できるサーバー向け
- 統合サーバー（シングルプレイ・LAN）でワールドを開いたとき、URL が設定されていれば、warn ログを1回出す（全ワールドで共通であること、パックを書き出すと配られ得ること）
- README に、上の2つの注意と `env:` の書き方を書く

**コスト・リスク**: 小。既存の値（https の URL）の意味は変わらない。

**推奨度**: 推奨（安全に関わり、小さい）

### P34. 初めて参加したプレイヤーに、外せる目標を配る（`firstJoinPresets`）

**目的と根拠**
- `defaultTargets` は全員に固定で、個人では外せない（`remove` は個人ターゲットだけを外す。`not_target` の文面 "or it is a global default"）。サーバーが「最初の目標」を配りつつ、各自が要らないものを外せるようにする手段が無い

**仕様案**
- Config `firstJoinPresets`（文字列リスト、既定 空 = 無効）: そのワールドに初めて参加したプレイヤー（ログインの時点で PlayerData が無かった人）に、列挙したプリセットを個人ターゲットとして適用する（`preset <name>` と同じ処理。上限 1024 件）
- この機能を入れる前から参加していたプレイヤー（PlayerData がある人）には適用しない。未知の ID は起動時とログイン時に warn ログを出して飛ばす。`presetsEnabled` が false なら何もしない
- 適用した旨を本人に1行（`message.itemmilestonelog.first_join_presets`、%s = 追加した件数）
- F37 の `prunedata` で消されたプレイヤーが戻ってきたときは「初めて」とみなされ、もう一度配られる（消されるのは目標が0件の人だけなので、配り直しで困ることは少ない）

**コスト・リスク**: 小。

**推奨度**: 推奨

### P35. インベントリでカーソルを合わせたアイテムを、キー1つで目標に追加

**目的と根拠**
- 目標を足す手段は、GUI のアイテム選択画面での検索、`add`（ID の入力）、`addhand`（手に持つ）だけ。チェストの中やクリエイティブの一覧で見つけたアイテムを、そのまま足せない

**仕様案**
- クライアントのキー割り当て「カーソルのアイテムを目標に追加」を足す。既定は割り当てなし（GUI を開くキーを既定なしにした issue #17 と同じ理由）
- コンテナの画面（インベントリ・チェスト・クリエイティブなど）で押したとき、カーソルの下のスロットにアイテムがあれば、そのアイテム ID・個数 1 で既存の `MilestoneActionPayload` の `ADD_TARGET` を送る。既存のペイロードと値を使うので通信の形式は変わらず（制約10）、1.0.1 のサーバーでも動く
- 結果の表示: サーバーは既存の処理どおりフィードバック付きの同期を返すが、現在のクライアントは Mod の画面が開いていないと同期を捨てる（`ClientMilestoneHandler.onSyncReceived`）。Mod の画面以外が開いているときは、同期のフィードバックをアクションバーに出すように変える
- 実装上の注意: 26.1.2 の `AbstractContainerScreen` では、カーソルの下のスロット `hoveredSlot` が protected で、取得する公開メソッドが無い（26.1.2 のクライアントの jar で確認）。アクセストランスフォーマーが要る見込み。1.21.1 は NeoForge のパッチで取得できるかを確かめる。キーの受け取りは NeoForge の `ScreenEvent.KeyPressed`（21.1.1 / 26.1.2 にある）
- Mod の GUI のデザインは変えない（キー割り当ての追加だけ）。R11（GUI への新しい操作）とは別物だが、新しい操作であることには変わりないので、制約1の範囲かはオーナーの判断

**コスト・リスク**: 小〜中。

**推奨度**: 推奨

### P36. アイテムのツールチップに記録の状態を出す

**目的と根拠**
- そのアイテムが自分の目標か、記録済みかを確かめるには、GUI か `targets` を開く必要がある

**仕様案**
- Mod 入りのクライアントで、アイテムのツールチップ（NeoForge の `ItemTooltipEvent`。21.1.1 / 26.1.2 にある）に行を足す: 目標で未記録なら「目標（未取得）」、記録済みなら「記録済み — <プレイ時間>」。数量ターゲットはキーごとに1行（最大3行、超えた分は「ほか N 件」）
- データ: クライアントは最新の同期（`SyncMilestonesPayload`）を保持する。サーバーはログイン時にも同期を送る（現在は GUI を開いたときと、記録などの変更のときだけ送る。1.0.1 のクライアントは画面が無いと同期を捨てるので、送っても害は無い）。1.0.1 のサーバーではログイン時の同期が無いので、GUI を一度開くまで出ない
  - 現在のサーバーは、記録のたびに Mod 入りの全クライアントへ同期を送っている（`syncPlayerIfOpen` はチャンネルの有無しか見ない）が、クライアントは画面が無いと捨てている。この候補を入れれば、その同期がツールチップの更新に使われる
- Config `itemTooltipStatus`（boolean、既定 true）。COMMON の設定はクライアントでは各自の PC のファイルが読まれるので、各自が切り替えられる
- R5（クライアント側の新しい表示）の理由のうち「バニラクライアントでは表示できない」は当てはまる（バニラクライアントでは何も変わらないだけ）。Mod の画面のデザインではないが、ゲームの表示を増やすので、制約1の範囲かはオーナーの判断

**コスト・リスク**: 中。

**推奨度**: 検討

### P37. 権限 Mod で管理者のコマンドを許可できるようにする

**目的と根拠**
- 管理者のコマンドは `.requires(hasPermission(2))`（OP の権限レベル2）だけで判定している。OP を渡さずに、一部のコマンドだけをスタッフに許可する運用ができない

**仕様案**
- NeoForge の権限 API（`PermissionAPI`、`PermissionGatherEvent.Nodes`、`PermissionNode`。21.1.1 と 26.1.2.71 のソースで存在を確認）に、ノード（例 `itemmilestonelog.command.admin`、`.exportall`、`.importall`、`.firsts.reset`、`.prunedata`、`.renameitem`、`.presets.manage`）を登録する。判定を「権限レベル2以上、またはノードが true」にする。ノードの既定は権限レベル2と同じにし、権限 Mod が無ければ挙動は変わらない
- 仕様書の制約2・11（既存の `.requires` を変えない）の例外になるので、オーナーの判断が要る
- 確かめること: コマンドの木は、クライアントへ送るときに `requires` で絞られるので、権限が変わったら送り直しが要る（権限 Mod が行うか）。26.x の Minecraft は独自の権限の仕組み（`Permissions` / `PermissionSet`。本 Mod の 26.1.2 の `MilestoneService` も使っている）を持つので、NeoForge の API との関係をバージョンごとに確かめる

**コスト・リスク**: 中。

**推奨度**: 検討（公開サーバーでの価値は大きいが、制約の例外になる）

### P38. NeoForge の設定画面を使えるようにする

**目的と根拠**
- 設定を変えるには toml を手で編集する必要がある。NeoForge には、Mod の設定から画面を自動で作る `ConfigurationScreen` と、それを Mod 一覧の「設定」ボタンに出す `IConfigScreenFactory` がある（21.1.1 / 26.1.2.71 のソースで確認）が、本 Mod は登録していない

**仕様案**
- クライアントで `IConfigScreenFactory` に `ConfigurationScreen` を登録する
- 各設定の表示名と説明の lang キー（`itemmilestonelog.configuration.<キー>` と `.tooltip`。NeoForge の `ConfigurationScreen` がこの規則でキーを引く）を en / ja に足す（1.2.0 までで約 40 項目）
- 注意: COMMON の設定はその PC のファイルなので、マルチプレイのサーバーに入っているときに変えてもサーバーには効かない（README と説明の文に書く）。26.3 の LOCAL 型の設定が画面に出るかは、26.3 の NeoForge で確かめる
- R5 は「新しい画面」を見送った。これは本 Mod の画面ではなく NeoForge の汎用の画面だが、画面が増えることは変わらないので、制約1・R5 の範囲かはオーナーの判断

**コスト・リスク**: 小〜中（コードは小さく、lang キーが多い）。

**推奨度**: 検討

### P39. Discord への投稿から自分を外す（個人の設定）

**目的と根拠**
- F14 は lookup などから記録を隠すが、Discord には従来通り投稿される（F14 の「隠していても変わらないもの」）。外部のサービスに自分の名前と記録が送られることを望まないプレイヤーが、それを止める手段が無い

**仕様案**
- `/milestonelog discordoptout`（OP 不要。トグル）。PlayerData に `excludeFromDiscord`（boolean、仕様書 §1.1 と同じ規則）を足す
- 外している人の分は、記録の投稿、F27 のまとめた投稿、F9 のダイジェスト、F19 に含めない
- Config `allowDiscordOptOut`（boolean、既定 true）。false なら、このコマンドは T の無効化メッセージを返し、設定は無視される（サーバーの方針で全員を投稿したい場合）

**コスト・リスク**: 小。

**推奨度**: 検討

### P40. 世界初だけを別の Webhook に送る

**目的と根拠**
- `discordNotifyScope` は `all` か `world_first` のどちらか一方。全記録を記録用のチャンネルに、世界初だけをお知らせ用のチャンネルに、という分け方ができない

**仕様案**
- Config `discordWorldFirstWebhookUrl`（文字列、既定 "" = 使わない）。設定されていれば、世界初の投稿はこちらだけに送る（二重に送らない）。`discordWebhookUrl` には、`discordNotifyScope` に従って世界初以外を送る
- F35 の 429・404 の扱いは URL ごとに行う。P33 の `env:` も使える

**コスト・リスク**: 小。

**推奨度**: 低

### P41. `firsts` に今の名前を出す

**目的と根拠**
- `firsts` は世界初の保持者の名前として、記録した時点の名前（`WorldFirstRecord.playerName`）を出している（`MilestoneCommands.firstsList`）。名前を変えたプレイヤーは古い名前で表示され、`lookup` や `admin` の名前と食い違う

**仕様案**
- 表示では、保存データにそのプレイヤーの最後の名前（`lastKnownName`）があればそれを使い、記録時の名前と違えば `message.itemmilestonelog.firsts_name_renamed`（%s = 今の名前、%s = 記録時の名前。en "%s (was %s)" / ja 「%s（旧: %s）」）にする
- 保存データ・export・API の `playerName` は変えない（記録時の名前という意味を保つ）

**コスト・リスク**: 小。

**推奨度**: 検討

### P42. プレイ時間と「Day」の表記をプレイヤーの言語に合わせる

**目的と根拠**
- チャットのプレイ時間は `Playtime.format` の `27h 03m 05s`、記録の整形は `(Day 5, 2026-11-23)` で、日本語の文面の中でも英語の表記になる（仕様書 F18 で「英語表記のまま」としたもの）

**仕様案**
- チャットと GUI だけ、lang キーで組み立てる（例 `message.itemmilestonelog.playtime_format`（%s = 時、%s = 分、%s = 秒）、`message.itemmilestonelog.record_day`（%s = 日）。ja 「27時間03分05秒」「5日目」）
- Discord・サーバーログ・出力ファイル・API は英語の書式のまま（機械で読む人がいるため）

**コスト・リスク**: 中。`formatRecord` は文字列を返し、多くの箇所で使われているので、Component を返す版を作って置き換える必要がある。

**推奨度**: 低

### P43. 版の違うクライアントとサーバーの参加を CI で確かめる

**目的と根拠**
- 仕様書 §3 の 〔X2〕 の確認（1.0.1 の Mod 入りクライアント ↔ 1.1.0 のサーバー、とその逆）は手動になっている。通信の互換（制約10）は、壊すと参加の時点で切断される影響の大きい部分なのに、自動の検査が無い。CI の mineflayer はバニラのプロトコルしか話さないので、Mod のチャンネルの交渉は確かめられない

**仕様案**
- CI で、仮想ディスプレイ（Xvfb）の上で本物のクライアント（`runClient` に `--quickPlayMultiplayer`）を起動し、別の版の Mod を入れた専用サーバーに参加させる。GUI を開くキーを押し、切断されないこと・同期を受け取ったことをログで確かめる。1.0.1 の jar はリリースの成果物から取る
- クラウドでの起動は 1.21.1 で実績がある（2026-11-22 に GUI のスクリーンショットを撮った手順）
- 1.1.0 の実装の前に入れれば、1.1.0 の通信の変更（無いはずだが）と 1.2.0 の F25 の追加ペイロードを、毎回自動で確かめられる

**コスト・リスク**: 中〜大。CI の時間が延びる（クライアントの起動に数分）。描画はソフトウェアで行うので、遅いが動く見込み。

**推奨度**: 検討

| R12 | ワールドごとに設定を上書きできるようにする | シングルプレイで設定が全ワールド共通なのは不便だが、NeoForge のワールドごとの設定（SERVER 型）は 26.3 で SYNCED 型になり、バニラクライアントの参加互換を壊す（仕様書 X1）。独自の上書きの仕組みは NeoForge の設定の仕組みを作り直すことになり、コストに見合わない。最も害の大きい Webhook の URL は P33 で扱う |
