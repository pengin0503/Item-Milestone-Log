### P15. 持ち運べる収納の中身も数える（opt-in）

**目的と根拠**
- Mod パックでは素材をバックパックやシュルカーボックスに入れて持ち歩くことが多く、数量ターゲット（例: ダイヤ ×1000）は「インベントリに同時に持つ」では達成しにくい

**仕様案**
- Config `countContainerContents`（boolean、既定 false）。true のとき、所持数にインベントリ内の収納アイテムの中身を加える: バニラのコンテナ（シュルカーボックスの内容）、バンドルの内容、NeoForge のアイテムのハンドラ（バックパックなど）。入れ子は1段まで
- 判定・進捗（Q9 / F1）・記録の確定のすべてに適用する

**コスト・リスク**: 中〜大。
- **1.0.1 の決定を覆す**（`QUANTITY_SPEC_1.0.1.md` Q2 と FEATURE_SPEC_1.0.1 F14 で「シュルカーボックスの中身・他 Mod のストレージは数えない」と決めている）
- スキャンのたびに収納の中身を読むため、負荷が増える（大きなバックパックを多く持つ場合）
- バックパックによっては中身をワールド側に持ち、ハンドラの取得でデータを読み込むものがある（Mod ごとの挙動の確認が要る）

**推奨度**: 要判断（採用するなら 1.1.0 ではなく、実際の Mod パックでの検証を前提に後の版を勧める）

**目的と根拠**

**コスト・リスク**: 小。ただし世界初については F7（`title %player% ...`）でも実現できるので重複がある。

**推奨度**: 低

### P19. 同時に起きた記録の通知をまとめる（チャット・音・Discord）

**目的と根拠**
- `Tracker.record` は記録1件ごとに、本人へのメッセージ、ブロードキャスト、世界初のアナウンス、サウンド、Discord の投稿を行う。スキャンで複数のターゲットを同時に満たすと、その件数分がすべて同じ tick に出る（`Tracker.onPlayerTick` が達成したキーごとに `record` を呼ぶ）
- これは珍しい状況ではない。所持しているアイテムは次のスキャンで記録されるので、プリセットの適用・`defaultTargets` の追加・Mod の導入直後のログイン・チェストからの一括移動で、数十件が一度に記録される
- Discord の Webhook には短時間の送信数の制限があり、超えると HTTP 429 になる。`DiscordNotifier.send` は 429 をそのまま捨てるので、まとめて記録された分の大半が Discord に届かない。チャットでも、他のプレイヤーの画面が数十行のブロードキャストで流れる

**仕様案**
- 同じ tick に同じプレイヤーで記録が `3` 件以上確定したら、通知をまとめる（2件以下は従来通り1件ずつ）
  - 本人: 「N 件を記録しました: A、B、C、D、E ほか M 件」の1通（名前は最初の5件まで）
  - ブロードキャスト: 受信者ごとに同じ形の1通（`muteBroadcasts` は従来通り）
  - 世界初: まとめた中に世界初があれば、アナウンスも「★ 世界初 N 件: …」の1通にまとめる
  - サウンド: 1回だけ鳴らす
  - Discord: 1通にまとめる（プレーンテキストは行を並べて 2000 文字以内、Embed（F4）は1通に最大 10 件の Embed を入れ、超えた分は最後の Embed に「ほか M 件」）
- イベント（`MilestoneRecordedEvent`、F2、F7、F20）は従来通り記録1件ごとに起こす（まとめるのは人に見せる通知だけ）
- Config `groupSimultaneousRecords`（boolean）。**既定値は要判断**: true を推奨（429 で届かない状態は不具合に近いため）。ただし 1.0.1 の挙動を変えるので、true にする場合は CHANGELOG に書く

**コスト・リスク**: 中。記録の確定を tick の終わりまで溜めてから通知する仕組みが要る（`ServerTickEvent.Post` で吐き出す）。F1・F5 の通知との順序も決める必要がある。

**推奨度**: 推奨

### P20. ターゲットを一括で外す（`presetremove` / `removeall`）

**目的と根拠**
- プリセットの適用は一度に多数のターゲット（上限 1024 件）を足せるが、外す手段は `remove` と GUI の1件ずつしかない（コマンドの一覧に一括の削除が無い）。プリセットを試しに適用して、やめたいときに困る

**仕様案**
- `/milestonelog presetremove <name>`（OP 不要）: そのプリセットのキーを個人ターゲットから外す。記録は消さない。`defaultTargets` のキーは外れない（従来通り）
- `/milestonelog removeall`（OP 不要）: 個人ターゲットをすべて外す。記録は消さない
- どちらも F23 の `undo` で元に戻せるようにする（F23 の取り消しの対象に「一括で外したターゲット」を足す）
- `presetsEnabled` が false なら `presetremove` は T の無効化メッセージ
- GUI には足さない（デザイン凍結）

**コスト・リスク**: 小。

**推奨度**: 推奨

### P21. `help` コマンド

**目的と根拠**
- サブコマンドは 1.0.1 で約20、1.1.0 の採用分で約20増える。バニラの `/help milestonelog` は引数の木をそのまま出すだけで、何をするコマンドか分からない

**仕様案**
- `/milestonelog help`（OP 不要）: そのソースが使えるサブコマンドだけを、1行ずつ短い説明つきで出す（権限・Config で無効なものは出さない）。説明は lang キー `message.itemmilestonelog.help.<name>`
- `/milestonelog help <subcommand>`: そのコマンドの書き方と説明

**コスト・リスク**: 小。lang キーが多く増える（en / ja とも）。

**推奨度**: 推奨

### P22. 長い一覧のページ分けと絞り込み

**目的と根拠**
- `list` / `targets` / `firsts` / `admin <player> list` / F6 の lookup は、全件を1行ずつ送る。Minecraft のチャット欄が保持するのは最近の 100 件のメッセージなので、数百件のターゲットを持つ Mod パックでは先頭が読めない

**仕様案**
- 既存のコマンドに、省略可能なページ番号を足す（`list <page>`、`targets <page>` など）。**ページ番号を省略したときは従来通り全件**（制約2）
- 1ページ 15 件。見出しに「ページ X / Y」。末尾に、クリックで次のページを実行する `[次へ]` を付ける（バニラの `ClickEvent` の `run_command`。バニラクライアントでも動く）
- `targets pending` / `targets done`: 未記録だけ・記録済みだけを出す（ページ番号と併用可）

**コスト・リスク**: 小〜中。コマンドの木が増える。

**推奨度**: 検討

### P23. `exportall` に世界初を含め、F22 の `importall` で戻す

**目的と根拠**
- `MilestoneExport.exportAll` は `players` だけを書き、世界初を含めない。F22 の仕様にも「世界初は復元されない」とある。サーバーの引っ越しやワールドの作り直しで、世界初だけが失われる

**仕様案**
- `all-players.json` に `worldFirsts` 配列（キー、保持者の UUID と名前、playTicks、day、epochMillis）を足す。`format` の値は変えない（読む側は知らないキーを無視する。1.0.1 の1人分の import はこの形式をそもそも拒否する）
- `importall` は世界初も読み込む。既に同じキーの世界初がある場合は、F24 と同じ規則（両方の epochMillis が分かれば早い方、不明があれば既存の方）
- 新しく入った世界初では、通知・Discord・イベントを起こさない。F17 の世界初の件数は書き込む

**コスト・リスク**: 小。

**推奨度**: 推奨（F22 を実装するなら一緒に）

### P24. 書き込み用の API（ターゲットの追加・削除、記録の付与）

**目的と根拠**
- `ItemMilestoneLogApi` は読み取り専用（`getRecord` / `getTargets` / `getTargetKeys` / `getWorldFirst`）。KubeJS やクエスト Mod から「この章に進んだらターゲットを足す」「クエストの報酬で記録する」といった連携ができない
- インベントリに入らない入手（AE2 などのストレージへの直接搬入、装備スロット系の Mod）は検出できない。パック製作者が自分で検出して記録させる手段があれば補える

**仕様案**
- `ItemMilestoneLogApi.addTarget(ServerPlayer, TargetKey)` / `removeTarget(ServerPlayer, TargetKey)`: 個人ターゲットの追加・削除（コマンドと同じ検証と上限）。戻り値は成功したか
- `ItemMilestoneLogApi.recordNow(ServerPlayer, TargetKey)`: 所持を確かめずに、通常の記録の経路（通知・世界初・イベント・Discord・F1〜F7 の連動）で記録する。実効ターゲットに無いキー、記録済みのキー、記録の一時停止中（クリエイティブ等）は何もせず false を返す
- サーバースレッドからだけ呼べる（他のスレッドからの呼び出しは例外）。README に KubeJS の例を書く

**コスト・リスク**: 中。公開 API を増やすので、以後の互換を守る範囲が広がる。

**推奨度**: 推奨（パック製作者向けの価値が大きい）

### P25. 管理者による他プレイヤーのターゲット操作と記録の付与

**目的と根拠**
- 管理者は他プレイヤーの記録を見る・消すことはできる（admin 系）が、ターゲットを足す・記録を付与することはできない。サーバーのイベントで特定の人に目標を配る、Mod を入れる前に手に入れていた分を個別に直す、といった運用ができない

**仕様案**
- `admin <player> add <item> [<count>]` / `admin <player> remove <item> [<count>]` / `admin <player> preset <name>`（権限レベル2）: 対象のプレイヤーのターゲットを操作する。オフラインのプレイヤーにも使える
- `admin <player> grant <item> [<count>]`（権限レベル2）: 所持を確かめずに記録する。記録時のプレイ時間は、対象がオンラインなら現在の値、オフラインなら保存されている最後の記録のうち最大の playTicks（無ければ 0）とし、epochMillis は現在時刻。**世界初は登録しない**（管理者の操作で世界初が動かないようにする）。本人へのメッセージだけを送り（オンラインなら）、ブロードキャスト・Discord・F7 は動かさない。`MilestoneRecordedEvent` は起こす
- 1.0.1 の「導入前のアイテムの『推定』マークは作らない」という決定（FEATURE_SPEC_1.0.1 F2）とは別物であることを README に書く（推定ではなく、管理者が明示的に付与する）

**コスト・リスク**: 小〜中。オフラインのプレイヤーのプレイ時間が分からない点は上の規則で割り切る。

**推奨度**: 検討

### P26. 英語・日本語以外の言語を追加しやすくする

**目的と根拠**
- 同梱の言語は en_us と ja_jp だけで、`ServerLang.BUNDLED_LANGUAGES` に固定で書かれている。翻訳を足すには、lang ファイルに加えてこのリストとテストを直す必要がある
- バニラクライアントへのメッセージ（`ServerLang`）は、この表に無い言語では英語になる

**仕様案**
- 同梱の言語の一覧をビルド時に lang フォルダから作る（`ServerLang` が読む索引ファイルを Gradle で生成する）か、リストに足すだけで済むことを README に書く
- テストを「en_us を基準に、他のすべての lang ファイルのキーとプレースホルダが一致する（欠けているキーは許すが、余分なキーとプレースホルダの不一致は失敗）」に変える。欠けているキーは en_us に戻して表示する（Minecraft の既定の動作と同じ）
- 翻訳そのものは、機械翻訳で同梱せず、利用者からの提供（PR など）を受け付ける形を勧める（品質を確かめられないため）

**コスト・リスク**: 中。

**推奨度**: 検討

### P27. Discord の送信の改善（Retry-After、スレッドへの送信の案内）

**目的と根拠**
- `DiscordNotifier.send` は HTTP 429 を受けると、その投稿を捨てる。Discord は 429 の応答に再試行までの待ち時間（`Retry-After`）を付けて返す
- Discord のフォーラムチャンネルやスレッドに送るには、Webhook の URL に `?thread_id=<スレッドの ID>` を付ければよい。現在のコードは URL をそのまま使うので既に動くはずだが、README に書かれていない

**仕様案**
- 429 のとき、`Retry-After` が 5 秒以下なら、その時間だけ待って1回だけ再送する。それより長い、または2回目も 429 なら捨てて warn ログ（従来通り）。送信は専用の1スレッドなので、待つ間は後続の投稿がキューで待つ（キューの上限 100 件は従来通り）
- README に `?thread_id=` の使い方を書く（動作を実機の Webhook で確かめてから）

**コスト・リスク**: 小。P19 で同時の投稿が減るので、429 自体が起きにくくなる。

**推奨度**: 検討（P19 を採用するなら優先度は下がる）

### P28. 拾得のたびに行う無駄な処理を減らす

**目的と根拠**
- `Tracker.tryRecordForItem`（拾得とクラフト/精錬の確認で呼ばれる）は、拾ったアイテムがターゲットかどうかを確かめる**前に**、インベントリ全体を数え（`countItemInPossession`）、実効ターゲット（`defaultTargets` + 個人ターゲット、最大 1024 件以上）の集合を新しく作っている。ターゲットと関係のないアイテムを拾うたびに、この処理が走る

**仕様案**
- 先に「そのアイテムの未記録のターゲットがあるか」を確かめ、無ければ何もしない
- 実効ターゲットを「アイテム ID → キーの一覧」の索引にして、ターゲットの変更・記録・Config の変更のときに作り直す

**コスト・リスク**: 小。ただし効果は小さい見込み（1回あたりマイクロ秒の単位）。大量のターゲットを持つプレイヤーが多いサーバーで、実際に計測してから判断するのがよい。

**推奨度**: 低

### P29. 古いプレイヤーデータの整理（`prunedata`）

**目的と根拠**
- `Tracker.onPlayerLoggedIn` は、参加したすべてのプレイヤーの PlayerData を作る（`MilestoneData.player` が `computeIfAbsent` で作る）。記録もターゲットも無いプレイヤーのデータも残り続け、消す手段は1人ずつの `admin <player> purge` しかない。公開サーバーでは `admin players` の一覧や F13 の集計が、一度来ただけのプレイヤーで膨らむ

**仕様案**
- PlayerData に最後に参加した時刻 `lastSeen`（long、§1.1 の規則）を足し、ログイン時に更新する
- `/milestonelog prunedata <days> [confirm]`（権限レベル2）: 記録が0件、個人ターゲットが0件、`lastSeen` が `<days>` 日より前（不明なものは対象外）のプレイヤーのデータを消す。`confirm` なしでは件数だけを返す（F24 と同じ形）。世界初は消さない

**コスト・リスク**: 小〜中。`admin` の下に置くと `admin <player>` の `<player>` と同じ位置になり、`prune` という名前のプレイヤーと区別できないので、F24 と同じくルート直下に置く。

**推奨度**: 低

### P30. サーバー全体の統計（`stats`）

**目的と根拠**

**仕様案**

**コスト・リスク**: 小。
