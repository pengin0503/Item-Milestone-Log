## P1. 表示に使うタイムゾーンの設定

**目的と根拠**
- 記録の日付（`yyyy-MM-dd`）は、チャット（`list` / `firsts` / admin / lookup）ではサーバーの既定のタイムゾーン、GUI ではクライアントのタイムゾーンで整形されている（`Playtime.formatDate` が `ZoneId.systemDefault()` を使い、GUI はクライアント側でそれを呼ぶ）
- 海外のホスティング（UTC が多い）で日本のプレイヤーが遊ぶと、チャットの日付が日本時間より最大9時間ずれ、同じ記録でもチャットと GUI で日付が違って見える

**仕様案**
- Config `displayTimeZone`（文字列、既定 "" = サーバーの既定）。`Asia/Tokyo` のような IANA の ID。`ZoneId.of` で解釈できない値は warn ログを1回出してサーバーの既定を使う
- 対象: サーバーが整形する日付すべて（チャット、F3 の HTML、F4 の Discord の `Date` 欄、F9 のダイジェスト）
- GUI は従来通りクライアントのタイムゾーン（見る人の現地時刻で表示するのが自然なため）。README に「チャットは設定のタイムゾーン、GUI は自分の PC のタイムゾーン」と書く

**コスト・リスク**: 小。保存データは epochMillis のままで変わらない。リスクはほぼ無い。

**推奨度**: 推奨

## P2. チャットのアイテム名にホバーでツールチップ

**目的と根拠**
- 記録・ブロードキャスト・世界初・進捗アラートのメッセージでは、アイテム名は文字だけで、似た名前の Mod アイテムを区別できない
- バニラのホバーイベント（アイテム表示）はバニラクライアントでも表示される

**仕様案**
- 上記メッセージのアイテム名の Component に、そのアイテムの既定のスタック（コンポーネント無し）を表示するホバーイベントを付ける。タグターゲットはタグの最初のアイテムを使う
- Config `chatItemHover`（boolean、既定 true）

**コスト・リスク**: 小。ホバーイベントの API は 1.21.1（`HoverEvent(Action.SHOW_ITEM, ItemStackInfo)`）と 26.x（`HoverEvent.ShowItem`）で異なる。メッセージ1通のサイズが少し増える。

**推奨度**: 検討（見た目の改善。優先度は中）

## P3. ランキングと最近の記録（`top` / `recent`）

**目的と根拠**
- マルチプレイでは「誰が一番多く記録したか」「ダイヤを一番早く取ったのは誰か」が話題になるが、今は OP が admin で1人ずつ見るしかない
- `broadcastMilestones` を切っているサーバーや、ログアウト中に起きた記録を、後から知る手段が無い

**仕様案**
- `/milestonelog top`: 記録数の多い順に上位10人（同数は最後の記録が早い順）と、実行者自身の順位
- `/milestonelog top <item> [<count>]`: そのターゲットを記録した人を、記録時のプレイ時間の短い順に上位10人と自分の順位（タグは `toptag <tag> [<count>]`）
- `/milestonelog recent [<n>]`: ワールド全体の最近の記録を epochMillis の新しい順に n 件（既定 10、最大 20）
- 権限は F6 の `allowLookup` に従う（false なら `isPrivileged` のみ）。P4 で隠しているプレイヤーは除く
- オフラインのプレイヤーも保存データから集計する

**コスト・リスク**: 小。全プレイヤーのデータを走査するが、コマンド実行時だけなので負荷は小さい。

**推奨度**: 推奨

---

## P4. 自分の記録を他人から隠す（`privacy`）

**目的と根拠**
- F6 の `allowLookup` は既定 true で、サーバー全体でしか切り替えられない。公開サーバーでは、見られたくないプレイヤーが自分だけ隠す手段があるとよい

**仕様案**
- `/milestonelog privacy`（OP 不要）: 実行のたびに切り替え、現在の状態を返す。PlayerData に `hideFromLookup`（boolean、true のときだけ書く）
- 隠している間は、他のプレイヤーの lookup・top・recent に出ない。`isPrivileged` を満たす者（OP・ホスト）、admin 系、exportall / exporthtmlall には従来通り出る
- ブロードキャストや世界初のアナウンスはサーバーの設定であり、この設定では止まらない（README に明記）

**コスト・リスク**: 小。

**推奨度**: 推奨（F6 または P3 を採用する場合）

---

## P5. 進捗アラートの個人ミュート（`muteprogress`）

**目的と根拠**
- F1 は既定で有効で、サーバー全体でしか切り替えられない。数量ターゲットを大量に持つプレイヤーには、アラートが多く感じられる場合がある。既存の `mutebroadcast` と同じく個人で止められるとよい

**仕様案**
- `/milestonelog muteprogress`（OP 不要）: 切り替え。PlayerData に `muteProgressAlerts`（boolean、true のときだけ書く）
- ミュート中も通知済みしきい値の更新は続ける（解除した直後に溜まっていた分がまとめて出ないようにする）

**コスト・リスク**: 小。

**推奨度**: 推奨（F1 を採用する場合）

## P6. プリセットの進捗表示（`presetprogress`）

**目的と根拠**
- `atm_star` のようなプリセットを追っているとき、あと何が残っているかを一覧で見たい。今は `targets` の全件から自分で探すしかない

**仕様案**
- `/milestonelog presetprogress <name>`（OP 不要）: 「<表示名>: 記録済み X / Y」と、未記録のキーの一覧（数量ターゲットは現在数つき）、このパックに存在しないためスキップしたキーの件数
- Y は F5 の「判定対象キー」R(S) の件数（F5 と同じ数え方）
- `preset` の下にリテラル `progress` を置くと、`progress` という ID の既存のカスタムプリセットが使えなくなる（予約語の追加は既存プリセットを壊す）ため、ルート直下の別コマンドにする
- `presetsEnabled` が false なら無効化メッセージ

**コスト・リスク**: 小。

**推奨度**: 推奨

## P7. スコアボード連携

**目的と根拠**
- バニラのスコアボードに記録数を載せれば、サイドバーやタブリストに表示でき（バニラクライアントでも見える）、データパックの `execute if score` からも使える。Mod 側の GUI を変えずに「見える化」できる

**仕様案**
- Config `scoreboardObjective`（文字列、既定 "" = 無効）。指定された名前の objective が無ければサーバー起動時にダミー基準で作る（表示名は「Milestones」）。既にあればそのまま使う
- 各プレイヤーのスコア = 記録数。記録確定、reset / resetall、import、admin の reset / resetall / purge、ログイン時に更新する
- 表示は利用者がバニラの `/scoreboard objectives setdisplay sidebar <名前>` で行う（Mod は表示位置を変えない）
- 任意で `scoreboardWorldFirstObjective`（世界初の保持数）も同じ方式で

**コスト・リスク**: 小〜中。スコアボード API はバージョンで差がある（ScoreHolder など）。他のデータパックが使っている objective の名前を指定すると、そのスコアを上書きする（README で専用の名前を勧める）。

**推奨度**: 推奨

## P8. Discord の言語設定

**目的と根拠**
- Discord への投稿は英語固定（`DiscordNotifier` の文面と、F4 の欄名）。日本語のコミュニティでは日本語の方が読みやすい

**仕様案**
- Config `discordLanguage`（`en_us` / `ja_jp`、既定 `en_us`）。文面と欄名を lang キー（`discord.itemmilestonelog.*`）にし、`ServerLang` の表から選ぶ
- アイテム名はサーバーの言語のまま（専用サーバーは英語の翻訳しか読み込まないため、`ja_jp` でもアイテム名は英語になる）。README に明記する

**コスト・リスク**: 小。lang キーが増える（en / ja とも）。

**推奨度**: 検討

## P9. Discord へのプリセット制覇通知

**目的と根拠**
- F5 の制覇はゲーム内のチャットにしか出ない。ATM Star の制覇のような大きな節目は Discord にも流したい

**仕様案**
- Config `discordNotifyPresetCompletion`（boolean、既定 false）。true かつ Webhook が設定されているとき、制覇を1通投稿する（`discordNotifyScope` とは独立）。形式は F4 の設定に従う

**コスト・リスク**: 小。

**推奨度**: 検討（F5 を採用する場合）

## P10. API の拡張（世界初フラグ・制覇イベント）

**目的と根拠**
- `MilestoneRecordedEvent` には、その記録が世界初かどうかが無い。KubeJS で「世界初なら報酬」を書くには、`getWorldFirst` を引いて比べる必要がある
- F5 の制覇を他の Mod / KubeJS から受け取る手段が無い

**仕様案**
- `MilestoneRecordedEvent#isWorldFirst()` を追加する（既存のコンストラクタは残し、世界初 = false とする）
- `PresetCompletedEvent`（`EVENT_BUS`、キャンセル不可）: `ServerPlayer`、プリセット ID、組み込みかどうか。F5 の判定で制覇したときだけ発火（import では発火しない）
- README の API の節に例を追加する

**コスト・リスク**: 小。公開 API への追加のみ（既存のメソッド・コンストラクタは変えない）。

**推奨度**: 推奨

## P11. データパックで配布できるプリセット

**目的と根拠**
- カスタムプリセットは config フォルダにあり、ワールドを別サーバーに移すと付いてこない（`CUSTOM_PRESET_SPEC_1.0.1.md` §2.3 で既知のトレードオフとされている）
- Mod パックの作者がプリセットをデータパック（KubeJS の data フォルダを含む）で配れれば、パックやワールドと一緒に配布できる

**仕様案**
- 読み込み先: `data/<namespace>/itemmilestonelog_presets/<id>.json`（形式はカスタムプリセットと同じ）。リロードリスナーで読み、`/reload` で再読み込みして GUI 利用者に再同期する
- ID はファイル名（既存と同じ `[a-z0-9_-]{1,32}`、サブフォルダ不可）。同じ ID の優先順位: 組み込み > config のファイル > データパック（複数のデータパックで重なったら namespace の辞書順で先のもの。衝突は warn ログ）
- データパックのプリセットは読み取り専用。`preset save` / `preset delete` で同じ ID を指定したら拒否する（専用のメッセージ）
- GUI へは既存の `PresetEntry` で「カスタム」として送る（ペイロード形式は変えない）。そのため一覧画面に削除ボタンが出るが、押してもサーバーが拒否して理由を返す。種類を正しく出したい場合は仕様書の制約10の方法（追加のペイロード）を使う

**コスト・リスク**: 中。リロードのタイミングと、config 側のプリセットとの合成が要る。GUI の削除ボタンの見え方に小さな不整合が残る（上記）。

**推奨度**: 検討（パック製作者向けの価値は大きい）

## P12. 全員分の import（`importall`）

**目的と根拠**
- `exportall` で全員分を書き出せるが、読み込みは1人分の形式しかない（`MilestoneExport.parseSinglePlayerExport` は `players` を持つファイルを拒否する）。ワールドの作り直しやサーバーの引っ越しで、OP が全員分を戻す手段が無い

**仕様案**
- `/milestonelog importall <fileName>`（権限レベル2）: `all-players.json` 形式を読み、各プレイヤーを UUID ごとに既存と同じ規則でマージする（ターゲットは和集合、記録は playTicks の小さい方）。UUID の無い・不正なエントリはスキップ
- 既存の import と同じく、イベント・世界初・Discord・F1 / F5 / F7 は動かさない。ファイルサイズの上限（10 MiB）も同じ
- `exportImportEnabled` が false なら無効化メッセージ

**コスト・リスク**: 小〜中。既存のパース・マージを再利用できる。

**推奨度**: 検討

## P13. リセットの取り消し（`undo`）

**目的と根拠**
- チャットの `/milestonelog resetall` は確認無しで全記録を消す（GUI には確認画面がある）。打ち間違いや思い違いで消した記録は、F10 のバックアップを手で戻すしかない

**仕様案**
- `/milestonelog undo`（OP 不要）: 自分の直前の `reset` / `resetall`（コマンド・GUI とも）を、10 分以内なら元に戻す。戻すのは消えた記録と、F1 / F5 の状態（`progressNotified` / `completedPresets`）
- 1段階のみ。メモリ上だけに持ち、ログアウトやサーバー停止で消える。世界初は reset で消えないので対象外
- 取り消しではイベント・通知・F7 を動かさない

**コスト・リスク**: 小。

**推奨度**: 推奨

## P14. アイテム ID の付け替え（`admin renameitem`）

**目的と根拠**
- Mod パックの更新でアイテムの ID が変わる（Mod の統合・改名）と、古い ID の記録・ターゲット・世界初が残り、新しい ID のアイテムでは記録済みと見なされない

**仕様案**
- `/milestonelog admin renameitem <oldId> <newId> confirm`（権限レベル2）: 全プレイヤーのターゲット・記録・`progressNotified` と世界初の `oldId` を `newId` に書き換える（個数はそのまま）。両方に記録がある場合は playTicks の小さい方を残す。件数を返し、サーバーログに残す
- 取り返しがつかない一括変更なので末尾の `confirm` を必須にし、実行前に F10 のバックアップを1回書く

**コスト・リスク**: 小〜中。使う場面は少ない。

**推奨度**: 低

## P15. 持ち運べる収納の中身も数える（opt-in）

**目的と根拠**
- Mod パックでは素材をバックパックやシュルカーボックスに入れて持ち歩くことが多く、数量ターゲット（例: ダイヤ ×1000）は「インベントリに同時に持つ」では達成しにくい

**仕様案**
- Config `countContainerContents`（boolean、既定 false）。true のとき、所持数にインベントリ内の収納アイテムの中身を加える: バニラのコンテナ（シュルカーボックスの内容）、バンドルの内容、NeoForge のアイテムのハンドラ（バックパックなど）。入れ子は1段まで
- 判定・進捗（Q9 / F1）・記録の確定のすべてに適用する

**コスト・リスク**: 中〜大。
- **1.0.1 の決定を覆す**（`QUANTITY_SPEC_1.0.1.md` Q2 と FEATURE_SPEC_1.0.1 F14 で「シュルカーボックスの中身・他 Mod のストレージは数えない」と決めている）
- スキャンのたびに収納の中身を読むため、負荷が増える（大きなバックパックを多く持つ場合）
- バックパックによっては中身をワールド側に持ち、ハンドラの取得でデータを読み込むものがある（Mod ごとの挙動の確認が要る）

**推奨度**: 要判断（採用するなら 1.1.0 ではなく、実際の Mod パックでの検証を前提に後の版を勧める）

## P16. 世界初・制覇のタイトル演出

**目的と根拠**
- 世界初やプリセット制覇はチャットの1行で流れてしまい、特別さが伝わりにくい

**仕様案**
- Config `celebrationTitle`（boolean、既定 false）。世界初と F5 の制覇のとき、本人の画面にバニラのタイトル / サブタイトルを表示する（バニラクライアントでも表示される）

**コスト・リスク**: 小。ただし世界初については F7（`title %player% ...`）でも実現できるので重複がある。

**推奨度**: 低

## P17. GUI の記録一覧に世界初の印

**目的と根拠**
- 世界初は `/milestonelog firsts` でしか分からず、GUI の記録一覧では自分の記録が世界初かどうか見えない

**仕様案**
- 新しい optional ペイロード `itemmilestonelog:sync_extra`（S2C）を追加し、「本人が世界初を保持しているキーの一覧」を送る（仕様書の制約10の方法。既存の `SyncMilestonesPayload` は変えない）。送るのは `hasChannel` が true のクライアントだけ
- GUI の記録行の先頭に「★」を付ける（テキストの追加のみ。レイアウトは変えない）
- 1.0.1 のクライアントはこのチャンネルを持たないので、従来通りの表示になる

**コスト・リスク**: 小〜中。追加ペイロードの最初の例になるので、後の拡張（P11 の種類の表示など）の土台にもなる。

**推奨度**: 検討

## P18. CSV 出力

**目的と根拠**
- 記録を表計算ソフトで集計したい利用者向け。F3 の HTML は見るためのもので、集計には向かない

**仕様案**
- `/milestonelog exportcsv` / `exportcsvall`（権限は F3 と同じ）。UTF-8（BOM 付き。Excel で日本語が化けないように）、RFC 4180 のクォート
- 数式インジェクション対策: `=` `+` `-` `@` で始まるセルは先頭に `'` を付ける（オフラインモードの名前やカスタムプリセット名が対象になり得る）

**コスト・リスク**: 小。

**推奨度**: 低

| R1 | ターゲットに関係なく、初めて手に入れた全アイテムを記録する（コレクションログ） | ATM10 規模ではプレイヤーごとに数千件になり、同期ペイロードの上限（4096 件）と GUI の表示に収まらない。データ量・設計とも 1.1.0 の範囲を超える |
| R2 | チーム（バニラのチーム）単位の共有マイルストーン | データモデル（記録の持ち主）が変わり、世界初・export・API のすべてに影響する。需要を確かめてから別の版で設計する方がよい |
| R3 | 累計獲得数による数量ターゲット | `QUANTITY_SPEC_1.0.1.md` §5 で「やらないこと」と決定済み |
| R4 | FTB Quests などとの直接連携 | 依存の追加になる（制約6）。F2 の advancement トリガー（FTB Quests は advancement を条件にできる）と API で代替できる |
| R5 | クライアント側のトースト通知や新しい画面 | GUI デザイン凍結（制約1）に反し、バニラクライアントでは表示できない。P16 のバニラのタイトルで代替できる |
| R6 | Discord のロールメンション（世界初で @role） | 既存の方針（`allowed_mentions` を空にしてメンションを一切飛ばさない）と逆行し、設定ミスで通知が大量に飛ぶリスクがある |
