## 採用しなかった候補

以下は提案時の内容のまま残す。後の版で検討し直す場合の資料とする。

### P15. 持ち運べる収納の中身も数える（opt-in）

**目的と根拠**
- Mod パックでは素材をバックパックやシュルカーボックスに入れて持ち歩くことが多く、数量ターゲット（例: ダイヤ ×1000）は「インベントリに同時に持つ」では達成しにくい

**仕様案**
- Config `countContainerContents`（boolean、既定 false）。true のとき、所持数にインベントリ内の収納アイテムの中身を加える: バニラのコンテナ（シュルカーボックスの内容）、バンドルの内容、NeoForge のアイテムのハンドラ（バックパックなど）。入れ子は1段まで
- 判定・進捗（Q9 / F1）・記録の確定のすべてに適用する

**コスト・リスク**: 中〜大。
- **1.0.1 の決定を覆す**（`QUANTITY_SPEC_1.0.1.md` Q2 と FEATURE_SPEC_1.0.1 F14 で「シュルカーボックスの中身・他 Mod のストレージは数えない」と決めている）
- スキャンのたびに収納の中身を読むため、負荷が増える（大きなバックパックを多く持つ場合）
- バックパックによっては中身をワールド側に持ち、ハンドラの取得でデータを読み込むものがある（Mod ごとの挙動の確認が要る）

**推奨度**: 要判断（採用するなら 1.1.0 ではなく、実際の Mod パックでの検証を前提に後の版を勧める）

### P16. 世界初・制覇のタイトル演出

**目的と根拠**
- 世界初やプリセット制覇はチャットの1行で流れてしまい、特別さが伝わりにくい

**仕様案**
- Config `celebrationTitle`（boolean、既定 false）。世界初と F5 の制覇のとき、本人の画面にバニラのタイトル / サブタイトルを表示する（バニラクライアントでも表示される）

**コスト・リスク**: 小。ただし世界初については F7（`title %player% ...`）でも実現できるので重複がある。

**推奨度**: 低

## 見送りを勧める案

| ID | 案 | 見送りの理由 |
|---|---|---|
| R1 | ターゲットに関係なく、初めて手に入れた全アイテムを記録する（コレクションログ） | ATM10 規模ではプレイヤーごとに数千件になり、同期ペイロードの上限（4096 件）と GUI の表示に収まらない。データ量・設計とも 1.1.0 の範囲を超える |
| R2 | チーム（バニラのチーム）単位の共有マイルストーン | データモデル（記録の持ち主）が変わり、世界初・export・API のすべてに影響する。需要を確かめてから別の版で設計する方がよい |
| R3 | 累計獲得数による数量ターゲット | `QUANTITY_SPEC_1.0.1.md` §5 で「やらないこと」と決定済み |
| R4 | FTB Quests などとの直接連携 | 依存の追加になる（制約6）。F2 の advancement トリガー（FTB Quests は advancement を条件にできる）と API で代替できる |
| R5 | クライアント側のトースト通知や新しい画面 | GUI デザイン凍結（制約1）に反し、バニラクライアントでは表示できない。バニラのタイトル表示は F7 の `title %player% ...` で出せる。（第3回の P36 のツールチップと P38 の NeoForge の設定画面は、オーナーが制約1の例外として採用した。トーストと本 Mod の新しい画面は引き続き見送り） |
| R6 | Discord のロールメンション（世界初で @role） | 既存の方針（`allowed_mentions` を空にしてメンションを一切飛ばさない）と逆行し、設定ミスで通知が大量に飛ぶリスクがある |

## 第2回で見送りを勧める案

| ID | 案 | 見送りの理由 |
|---|---|---|
| R7 | 放置（AFK）していた時間をプレイ時間から除く | 記録のプレイ時間はバニラの統計 `play_time` で、既存のすべての記録と世界初の比較がこれに基づく。途中から意味を変えると新旧の記録を比べられなくなる。放置の判定も推測で、誤判定の苦情を招く |
| R8 | Curios などの装備スロットの中身を数える | Mod ごとの API への依存が要る（制約6）。P15（収納の中身）を採用しなかった判断とも合わない。必要なパックは F32（候補 P24）の API で自分で記録させられる |
| R9 | 記録した場所（座標）を残す | lookup・export・Discord を通じて、拠点の場所が他人に知られる。ディメンションだけなら問題は小さいが、公開 API の `MilestoneRecord` の形を変える必要があり、価値に見合わない |
| R10 | Discord の投稿にアイテムの画像を付ける | アイテムのテクスチャを外部に置く手段が要り、外部サービスへの依存か、画像のホスティングが必要になる |
| R11 | GUI に検索・並べ替え・ページなどの新しい操作を足す | GUI のデザイン凍結（制約1）に反する。凍結を解く判断をするなら、その時に改めて検討する。（第3回の P35 は本 Mod の画面の外のキー割り当てで、オーナーが制約1の例外として採用した。本 Mod の画面への新しい操作は引き続き見送り） |

## 第3回で見送りを勧める案

| ID | 案 | 見送りの理由 |
|---|---|---|
| R12 | ワールドごとに設定を上書きできるようにする | シングルプレイで設定が全ワールド共通なのは不便だが、NeoForge のワールドごとの設定（SERVER 型）は 26.3 で SYNCED 型になり、バニラクライアントの参加互換を壊す（仕様書 X1）。独自の上書きの仕組みは NeoForge の設定の仕組みを作り直すことになり、コストに見合わない。最も害の大きい Webhook の URL は P33（仕様書 F39）で扱う |
| R13 | アイテム以外のマイルストーン（advancement の達成、討伐、ディメンションへの到達など） | Mod の範囲（アイテムの初取得）を超える。バニラの advancement と統計が既にあり、F2 で advancement と連携できる |
| R14 | 記録した経路（拾得・クラフト・スキャン）を残す | スキャンで見つかったものは経路が分からない（機械・チェスト・`/give` の区別ができない）。公開 API の `MilestoneRecord` の形を変える必要があり、価値に見合わない |
