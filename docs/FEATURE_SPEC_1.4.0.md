### F-140-1. MilestoneData への明示的な schemaVersion 導入（N88）

#### 仕様
- `MilestoneData` のルートに `schemaVersion`（int）を導入する。定数 `CURRENT_SCHEMA_VERSION = 1` を共通ロジック側（新設 `SchemaVersionLogic` または `MilestoneData` 自体。実装時に既存の配置流儀で決める）に置く。
- 読み込み規則:
- フィールド無し → **0** として扱い、通常どおり読み込む（〜1.3.1 の全データが該当）。
- 値が 0〜CURRENT の範囲 → 通常どおり読み込む。
- 値が CURRENT より大きい（将来版のデータ）→ **読み込みは従来どおり lenient に行い**（要素単位の読み飛ばし方針は変えない）、warn ログを 1 回出す（「newer schemaVersion X, loading best-effort」旨）。読み込み自体は失敗させない。
- 値が不正（数値でない、負数）→ warn ログを出して 0 として扱う（要素単位スキップと同じ方針）。
- 書き出し規則:
- 常に `schemaVersion` を書く。値は `max(CURRENT, 読み込み時に保持した値)` とする（D-140-1: 将来版の値をダウングレード保存で潰さない）。
- 新規ワールド（読み込み実績なし）は CURRENT を書く。
- **schemaVersion を上げる条件（今後の運用規則として本書で固定）**: 保存形式に「移行処理なしでは読めない変更」を入れるときだけ上げる。lenient な任意フィールド追加（欠落＝既定値で読めるもの）では上げない。したがって第2バッチのプリセット関連の永続化追加でも原則上げない。
- F10 自動バックアップは SavedData ルートタグをそのまま書くため、`schemaVersion` は自動的にバックアップにも含まれる（追加作業なし。テストで確認する）。
- export／import の JSON 形式には `schemaVersion` を**入れない**（export 形式の版管理は本件の対象外。必要になれば別案とする）。

#### 実装メモ
- 現行コード（1.21.1 で確認）: `MilestoneData.load(CompoundTag, …)`／`save(CompoundTag, …)` が NBT 経路。26.x は Codec 経路（`DataCompat`）＋ `readLegacy`。両経路に同じ規則を実装し、値の正規化・保持の判断は共通の純粋関数に切り出して単体テスト可能にする。
- 保持値の置き場所: `MilestoneData` のインスタンスフィールド（永続化対象そのものとは別に「読み込んだ schemaVersion」を保持）。`setDirty` の要否は値が変わるときのみ従来規則に従う。

#### テスト要件
- 単体: 正規化関数（無し→0／0／1／2（将来）／負数／非数値）全ケース。
- ラウンドトリップ: 1.3.1 形式フィクスチャ（フィールド無し）→ 読込 → 保存で `schemaVersion=1` が付き、本体データが不変。将来値 99 のフィクスチャ → 読込 → 保存で 99 が保持される。
- 移行: 1.21.1→26.x の移行テスト（既存 CI のワールド移行テスト）に `schemaVersion` の保持を確認するケースを追加。
- バックアップ: F10 バックアップファイルに `schemaVersion` が含まれることを既存バックアップテストへ追加。

### F-140-2. MilestoneData 読み込み時の破損前データ自動退避（N141）

#### 前提確認（実装の最初のステップで行う調査）
- バニラの `DimensionDataStorage` がファイル破損時にどう振る舞うか（読込失敗で空データとして扱い、次の保存で元ファイルを上書きするか／`.dat_old` 等の退避が既にあるか）を 1.21.1 と 26.x で確認する。本 Mod の lenient 読込（要素単位スキップ）は「ファイルは読めたが中身の一部が壊れている」ケースを既に救っているので、本件の主対象は (a) 要素スキップが発生したケース、(b) ルート構造の異常・Codec 全体失敗でデータが空／欠落になるケース、の 2 つに定める。調査でバニラ側の退避が十分と判明した範囲は本件の対象から外し、調査結果を PR 説明に残す。

#### 仕様
- 読込結果の集計: `MilestoneData` の読込（NBT／Codec 両経路）で、要素単位スキップ件数と「全体失敗」フラグを数える共通の仕組みを入れる（既存の warn ログ箇所が集計点になる。新設の純粋ロジック `CorruptionEvacuationLogic` に判断を置く）。
- 退避の発火（D-140-2）: サーバー開始時（`ServerStarting`／`Started` のうち、MilestoneData の初回読込が終わり、かつ通常保存で元ファイルが上書きされるより前）に、集計結果が「スキップ ≥1 件 or 全体失敗」の場合のみ、ディスク上の現行 SavedData ファイルを退避先へ**コピー**する（元ファイルは消さない）。
- 退避先: `<world>/itemmilestonelog/corrupt/`（F10 バックアップの `<world>/itemmilestonelog/backups/` の姉妹）。
- ファイル名: `itemmilestonelog_data-yyyyMMdd-HHmmss.dat`（バックアップと同じ日時形式・タイムゾーン規則＝`displayTimeZone`）。同名衝突時は F10 と同じ連番方式。
- あわせて同名 `.txt` の要約（読込日時、スキップ件数、全体失敗の有無、元の schemaVersion）を書く。プレイヤー名・記録内容などのデータ本体は要約に含めない。
- 退避は最新 **5 件**まで保持し、古いものは自パターンに一致するファイルだけを削除する（F10 の世代管理と同じ安全規則）。
- 正常読込（スキップ 0 件）では何もしない。退避処理の失敗は warn ログのみで、サーバー開始を止めない。
- 退避した旨はサーバーログに warn で明示する（退避先パスと件数）。チャットやプレイヤーへの通知はしない（運用者向け機能のため）。
- Config は追加しない（§2.2）。

#### 実装メモ
- SavedData ファイルの実パス解決は版ごとの DataStorage の流儀に従う（オーバーワールドの data フォルダ＋ `DATA_NAME`）。解決できない版・環境では退避を諦めて warn ログのみ（開始は止めない）。
- コピーは F10 の原子的書き込みと同じく一時ファイル経由にする必要はない（読み取り専用コピー）が、コピー中に元ファイルが書き換わらないタイミング（サーバー開始直後・初回保存前）で行うことを実装で担保する。

#### テスト要件
- 単体: 退避判断（スキップ 0→しない／≥1→する／全体失敗→する）、ファイル名生成、世代 prune の選択（パターン外ファイルを消さない）。
- 統合: 壊れた要素を含むフィクスチャでサーバー（GameTest／ボットテスト基盤）を起動し、退避ファイルと要約ができ、本体データの読める部分が保持されることを確認。正常フィクスチャでは退避が起きないことも確認。

### F-140-3. importall と自動バックアップの非同期 I/O 化（N45）

#### 仕様
- Mod 専用の単一スレッド Executor（名前 `itemmilestonelog-io`、デーモンスレッド）を新設する。ライフサイクル: サーバー開始時に生成し、§F-140-4 のドレインを経て停止時にシャットダウンする。統合サーバー（シングルプレイ）でワールドを出入りしても再生成できること（停止済み Executor の再利用をしない）。
- キューは直列実行とし、タスク間の順序を保証する（バックアップ同士、import 同士、バックアップと import の前後関係が入れ替わらない）。
- 対象 1: **自動バックアップ（F10）**
- サーバースレッドで行うのは NBT ルートタグへのシリアライズ（`toSavedDataFileTag` 相当。在メモリデータへのアクセスはサーバースレッドでのみ行う）まで。ディスク書き込み（一時ファイル＋原子 move、世代 prune）は Executor で行う。
- レート制限（1 時間に 1 回。停止時は無視）の判定は従来どおりサーバースレッド側で、従来と同じタイミングで更新する（書き込み失敗時の扱いは従来どおり：次回保存時に再試行され得る）。
- `writeBackupNow`（F24 renameitem 前のバックアップ）は**同期のまま**とする（呼び出し側が「書けたこと」を前提に処理を進めるため）。Executor 経由にしない理由をコードコメントに残す。
- 対象 2: **importall（F22）**
- ファイルの読み取りと JSON パース・マージ計算は Executor で行い、結果の `MilestoneData` への適用とフィードバック送信はサーバースレッドへ戻して行う（`server.execute` 相当）。
- コマンドのフィードバックは 2 段階になる（D-140-5）: 受付時に「読み込みを開始した」旨、完了時に従来どおりの結果（取込件数等）、失敗時に失敗した旨と理由の要約。lang キーを新設する（en/ja）。
- 実行中の importall があるときの次の importall は受け付けず、その旨のメッセージを返す（二重適用の防止）。通常の `import`（単一プレイヤー分）は本件の対象外とし同期のまま（規模が小さく、対話的操作のため）。
- Executor が満杯／停止中などで投入できない場合は、そのタスクに限って従来の同期経路で実行し、warn ログを残す（データ安全を可用性より優先する）。
- 記録の確定・スキャン等のゲームプレイ経路は一切非同期化しない（本件の対象は上記 2 つだけ）。

#### 実装メモ
- 現行の同期経路（1.21.1 で確認）: `MilestoneBackup.onLevelSave`／`onServerStopping`／`writeBackup` がサーバースレッドで圧縮書き込みまで実施。`MilestoneExport` の importall がコマンド実行スレッドでファイル I/O とマージを実施。
- シリアライズ済みタグと書き込み先パスなど、Executor へ渡す値は不変スナップショットにする（サーバースレッド側の可変状態を Executor から参照しない）。
- 純粋ロジック（投入可否、実行中フラグ、フォールバック判断）は common 側に切り出して単体テスト可能にする。

#### テスト要件
- 単体: 投入・直列順序・実行中 import の二重投入拒否・フォールバック判断。
- 統合: 既存の importall／バックアップのボットテスト・GameTest が従来と同じ最終結果になること（非同期化で結果が変わらないこと）。バックアップファイルの内容が同期時と同一形式であること。
- 負荷の目安: 大きな import ファイル（既存フィクスチャの最大級）でサーバースレッドがブロックしないことを、テストログの所要時間で確認する（厳密なベンチマークは本件の対象外）。

### F-140-4. サーバー停止時の非同期処理ドレイン待機（N149）

#### 仕様
- `ServerStopping` の処理順序を次のとおり固定する（現行 `ItemMilestoneLog.onServerStopping` の置き換え）:
1. 新規タスクの受付を止める（これ以降の投入は同期フォールバック側へ回す。ただし停止処理中の投入は最終バックアップを除き発生しない設計にする）。
2. §F-140-3 の Executor のキューが空になるまで最大 **30 秒**（D-140-3）待つ。待機中、5 秒ごとに残タスク数を info ログへ出す。
3. 最終自動バックアップ（F10 の停止時バックアップ。レート制限無視は従来どおり）を Executor の最終タスクとして投入し、その完了もドレイン待ちに含める。ドレインがタイムアウトした場合は最終バックアップを**同期書き込みにフォールバック**して実行する。
4. タイムアウト時は未完了タスクを中断し、件数と種類を warn ログに残す。停止処理自体は継続する（サーバーの停止を無期限に引き延ばさない）。
5. 既存の停止処理（`DiscordNotifier.shutdown`、保留通知・コマンド・UNDO のクリア等）は従来どおり行う。順序は「ドレイン完了（またはタイムアウト処理）→ 最終バックアップ確定 → 既存クリア処理 → Executor シャットダウン」とする。
- `ServerStopped` では Executor の状態をリセットし（次ワールドで再生成可能にする）、既存の `MilestoneBackup.resetState` 等も従来どおり呼ぶ。
- Config は追加しない（§2.2）。待ち上限 30 秒は定数とし、純粋ロジック側でテスト可能にする。

#### テスト要件
- 単体: ドレイン判断（空→即完了／制限時間内完了→完了／超過→タイムアウト＋フォールバック選択）。
- 統合: importall 実行直後にサーバー停止を行い、取込結果と最終バックアップの両方が失われないことをボットテスト／GameTest で確認。意図的に長いタスクを積んだ状態の停止で、30 秒＋フォールバック時間を超えて停止が延びないことを確認。

## 3. 第2バッチ（プリセット基盤）— 骨子（詳細は第1バッチ承認後に F 節へ展開する）

第2バッチは §5 順序どおり **G-B → G-C →（余力で）プリセット系個別案**。ここでは設計の固定点と判断事項だけを示し、永続化フィールド表・コマンド仕様の完全な F 節化は第1バッチの承認後に行う（本ドラフトの承認対象は主に第1バッチ）。

### 3.1 G-B: プリセット定義フォーマット拡張（N17／N19／N65／N101／N106）

現行（1.21.1 で確認）: `Presets.PresetDefinition(id, name: PresetName, items: List<TargetKey>, kind)`。JSON は `name`（文字列 or 多言語オブジェクト、F54）と `items`（文字列 or `{item, count}`）のみで、未知フィールドは読み捨てられる。GUI 保存（`saveCustomTo`）は `name` だけを引き継ぎ、それ以外のフィールドは書かない。

固定点:
- 新フィールドはすべて**任意**とし、欠けたプリセット（既存ファイル・組み込み・データパック）は従来どおり動く（後方互換）。`PresetDefinition` は新フィールドに既定値を持つ形へ拡張する（既存コンストラクタの互換を保つ）。
- JSON フィールド案:

| フィールド | 型 | 既定 | 内容 |
|---|---|---|---|
| `includes` | 文字列配列（プリセット ID） | [] | N17: 他プリセットの items を取り込む。再帰展開し、循環は検出して warn＋その枝を切る。存在しない ID は warn＋スキップ。重複は既存の dedup 規則（出現順保持）に従う。展開は「includes を列挙順に展開したもの＋自前の items」の順 |
| `description` | 文字列 or 多言語オブジェクト | なし | N19: `name`（F54）と同じ形式・解決規則を流用 |
| `category` | 文字列 | なし | N19: 自由文字列（長さ上限と制御文字の除去のみ検証）。一覧の並び・絞り込みは個別案側で使う |
| `order` | int | 0 | N19: 一覧の並び替えキー（order 昇順→ID 順）。全プリセット 0 のときは現行の ID 順と同一になり互換が保たれる |
| `version` | int（1 以上） | なし（無版） | N65: プリセット内容の版。案内部分は G-C（§3.2） |
| `requiredMods` | 文字列配列（mod id） | [] | N101: 必要な Mod が無い環境では適用をスキップし、不足分をフィードバックする（一覧への表示は残す — D-140-6） |
| `groups` | オブジェクト配列 `{id, name?, items}` | [] | N106: items の部分集合による段階グループ。グループ外の items は「グループなし」として扱う。items に無いキーを指す要素は warn＋落とす。同一キーの複数グループ所属は先勝ち＋warn |

- **GUI 保存時の引き継ぎ**: `saveCustomTo` が新フィールドを落とさないこと（G2 の `name` 引き継ぎと同じ規則で、既存ファイルの有効な新フィールドは保持する）。GUI レイアウトは変えない（制約1）。新フィールドの編集 UI は作らない（手書き JSON 専用）。
- 検証・解決（includes 展開、循環検出、groups 検証、requiredMods 判定のうち純粋部分）は common 側の純粋ロジックにし、単体テストする。
- データパックプリセット（F21）・組み込みプリセットにも同じ形式を適用する（組み込み 2 件は移行作業なし＝新フィールド無しで従来動作）。

判断事項:
| # | 事項 | 推奨 |
|---|---|---|
| D-140-6 | `requiredMods` 不足のプリセットを一覧（コマンド／GUI 同期）に出すか | **出す**（適用時だけ不足を伝えてスキップ）。出さないと存在自体が分からず、パック制作者が混乱するため。GUI はレイアウト不変の範囲で既存の一覧に含めるだけ |
| D-140-7 | `groups` の制覇判定への影響 | 1.4.0 では**変えない**（制覇は従来どおり R(S) 全体）。グループ別進捗は表示・レポート側（N07／N128 等）で使う |

### 3.2 G-C: プリセット自動追加フロー（N18／N102、N65 の案内部分）

固定点:
- **N18 `nextPresets`**: プリセット JSON に `nextPresets`（プリセット ID 配列）を追加。プレイヤーがそのプリセットを**新たに制覇したとき**（F5 の `completedPresets` への追加と同じ判定点）に、次プリセットの targets を個人 targets へ自動追加する（F33 の適用関数と `firstJoinPresets` の流儀を再利用）。既に制覇済みのものへの遡及適用はしない。連鎖は制覇イベント駆動なので循環しても `completedPresets` で止まる。フィードバックの lang キーを新設する。
- **N102 `unlockAfterHours`**: プリセット JSON に `unlockAfterHours`（数値、時間）を追加。プレイヤーの累計プレイ時間がしきい値に達したら、そのプリセットの targets を自動追加する。判定点はログイン時＋Tracker のスキャン周期に相乗る軽いチェック（毎スキャンの単純比較のみ）。**一度自動追加したプリセットは、プレイヤーが targets を外しても再追加しない**ため、PlayerData に自動追加済みプリセット ID の集合を永続化する（フィールド名は F 節化時に確定。§2.1 の表へ追加し、schemaVersion は §F-140-1 の規則により上げない）。
- **N65 の案内**: プレイヤーが適用済みのプリセットについて、現在の `version` が「そのプレイヤーが最後に見た version」より大きければ、ログイン時に差分の要約（追加／削除された目標数）を 1 回だけ知らせる。最後に見た version は PlayerData にプリセット ID→version のマップとして永続化する（N102 の自動追加済み集合と合わせて「プリセット適用状態」として F 節化時に設計を一本化する — D-140-8）。
- いずれも `presetsEnabled=false` のときは動作しない（既存スイッチに従う。新規 Config は作らない）。

判断事項:
| # | 事項 | 推奨 |
|---|---|---|
| D-140-8 | N102／N65 の永続化を 1 つの「プリセット適用状態」にまとめるか | **まとめる**（プリセット ID → {適用済みか、最後に見た version}）。別々に足すと後片付け規則（resetall／purge 等との関係）が二重になるため。後片付け規則は F 節化時に §1.1 の流儀で表にする |

### 3.3 余力で入れるプリセット系個別案（§5 順序どおり）

G-C の後に余力があれば、この順で F 節化する: **N07**（`preset show`。コマンド追加のみ。`show` は予約 ID と衝突しないことを確認済み）→ **N53**（`preset diff`。N07 と表示基盤を共有）→ **N54**（`preset share`。共有コードの形式・長さ上限が論点）→ **N56**（`renametag`。F24 のタグ版）→ **N108**（`strictPresetValidation` Config、既定 false。true のとき不正要素のあるプリセットファイルを丸ごと不採用にする）→ **N140**（プリセット JSON Schema の同梱。追加依存なしの制約のため、スキーマ検証テストは Gson による構造チェックで代替する旨を明記）。
いずれも入らない場合は 1.5.0 へ送る（1.4.0 のスコープに含めるかは第2バッチ着手時に pen と再確認する）。
