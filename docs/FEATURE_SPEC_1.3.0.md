# Item Milestone Log — 追加機能 実装仕様書（v1.3.0）【ドラフト：採否判断用】

この文書は、v1.3.0 以降の機能候補（提案リスト `feature_proposals_1_3_0.md` の N01〜N150）を、オーナー（pen）が採否を判断できる形に整理したドラフトである。対象リポジトリ: pengin0503/Item-Milestone-Log

> **この文書の位置づけ**: 1.1.0 / 1.2.0 のときと同じ流れで、まず候補を整理し、pen の採否決定を受けた案についてのみ、この後の改訂で詳細仕様（F 節形式）へ起こす。**現時点では実装着手しない。** 採否欄はすべて空欄であり、推奨マークは Muse の整理上の提案にすぎない。
>
> 共通制約は `docs/FEATURE_SPEC_1.1.0.md` §1 を引き続き適用する（GUI レイアウト変更禁止、既存コマンド構文の不変、SavedData 後方互換、ネットワーク互換は optional ペイロード追加のみ、等）。本ドラフトで新たに判断が必要な前提変更は §0 に集約した。

## 0. pen が判断すべき前提事項

### D1. 「バニラクライアント参加互換は必須」という原則を外すか

- 提案書はこの原則を「必須条件から外す」ことを前提に書かれている。1.2.0 までの設計原則（サーバー側のみで完結し、バニラクライアントがそのまま参加できる）からの転換点なので、最初に判断してほしい。
- **実態**: 150 件のうち、バニラ互換を実際に壊すのは **N30（カスタム効果音イベントの同梱）だけ**。残りは「バニラ互換」105 件、「クライアント任意」（Mod 導入クライアントだけ追加機能、バニラ参加は妨げない）24 件、「内部改善・開発運用」19 件など、原則を維持したままでも実装できる。
- **Muse の推奨**: 原則は維持し、N30 だけを例外として個別に判断する（N30 を採用する場合も、効果音イベントの登録自体はサーバー参加条件にせず、リソースパック差し替え可能な任意機能として設計できる余地がある）。

### D2. 大規模な 2 件（N24 / N44）の扱い

- **N24 DataComponent / エンチャント条件付きターゲット（大）**: `TargetKey` の拡張で SavedData・プリセット・API のすべてに波及する。提案書自身が「検討枠・中長期候補」としている。推奨: 1.3.0 では採用せず、需要を見て別途設計枠にする。
- **N44 コアクラス責務分割リファクタリング（大）**: 機能追加と同一 PR に混ぜるとレビューと切り分けが不能になる。推奨: 採用する場合も 1.3.0 の機能実装とは分離し、単独の内部改善として実施する（実施時期は pen 判断）。

### D3. 内部品質・運用 23 件の置き場所

- この区分は利用者向け機能とは性質が別で、リリースに同梱する必然性が薄いものが多い。推奨: **N43（.gitignore 修正）は実害があるので 1.3.0 を待たず先行実施**（§3）。基盤に影響する N88（schemaVersion）は 1.3.0 の最初に置く。その他は「随時実施してよいメンテナンス枠」として 1.3.0 の採否とは分けて判断する。

### D4. リリースの分け方

- 全件採用すると 1.3.0 としては大きすぎる（小 118 件でも総量は 1.2.0 の数倍）。採用が決まったら §5 の実施順序案をもとに、必要なら 1.3.0 / 1.4.0 に分割する。これは採用数を見てから決めればよい。

## 1. 整理の方針

- 各案について、既存機能（F1〜F54、1.1.0 / 1.2.0）との関係を「拡張（既存 F の上に乗る）」「新規」「統合先グループ」のいずれかで明記した（§4 の採否表）。
- 近接・重複する案は §2 のグループに束ねた。グループ内の案は原則として同時設計する（別々に実装すると設定の優先順位や基盤が二重になる）。
- 過去に不採用・見送り済みの P15・P16・R1〜R19 は提案書側で除外済みであり、本ドラフトでも扱わない。

### 個別の重複・依存メモ

- N08（copytargets、個人用）と N97（admin copyfrom、管理者用）は対の機能。実装は共有できるので同時採否が効率的（片方だけでも可）。
- N51（targets near）と N104（loginPendingSummary）は進捗率の計算を共有する。N104 は F52 の姉妹機能。
- N06（キーワードフィルタ）と N96（種別フィルタ）と N100（統合検索）は targets/list の絞り込み基盤を共有できる。
- N56（renametag）は F24（renameitem）のタグ版で、安全性ルールと実装の大半を流用できる。
- N11 は 1.2.0 仕様書 F8b で「必要になったら別に検討」と明記されていた積み残し。
- N46（差分同期）と N148（同期上限の警告）は同じ同期経路。N46 をやるなら N148 の通知改善はその一部になる。
- N48（同一ファイル同期スクリプト＋ README 分割）と N86（ドキュメント整合性 CI）は、N48 の README 分割後に N86 を作る方が効率的。
- N73（テキスト進捗バー）は区分が「バニラ互換」で、サーバー側の表示拡張。クライアント体験カテゴリだが実装はサーバー側。
