- 状態: **pen レビュー待ち（2026-11-24）**。本設計の承認後に本実装へ進む。
- 対象仕様: `docs/FEATURE_SPEC_1.3.0.md` §8（N251）、§9（N252）、§10（1.3.0 スコープ）、§11（1.20.1 の位置づけ）
- 成果目標: 配布 JAR を現行 4 本（1.21.1 / 26.1.2 / 26.2 / 26.3）から **2 本**（1.21.x 系 1 本 + 26.x 系 1 本、1.21.x が分割になる場合は 3 本）にする。対応範囲は 1.21.1〜1.21.11（+検証が通れば 1.21 無印）と 26.1.2〜26.3 に広がる。

## 0. 結論サマリ（判断事項）

1. **方式**: 仕様書 §8 の方針（最古版基準でコンパイル＋非互換箇所を互換クラスに隔離）を採用する。ただし §1 の再実測により、26.x 間の差分には**バイナリ互換を壊す変更**（クラスのパッケージ移動、フィールド/メソッドの削除・改名、レコード成分の型変更）が複数含まれることが確定した。したがって互換の単位は「メソッド内の分岐」ではなく「**バージョン別実装クラス**」とし、起動時に検出した MC バージョンで実装を選ぶ。選ばれなかった版のクラスは一切ロードしない（ロードしなければ、そのクラスが参照する存在しない API に触れることはない）ことが設計の要になる。
2. **N246（PlatformBridge）の前後**: **N246 は 1.3.0 の前にやらない**。理由は (a) 差分面が小さく、必要な互換インターフェースは 4 系統のみ（§2.2）で、全面 PlatformBridge 化は過剰、(b) N246 は「単独実施」が pen 決定済みで、1.3.0 と混ぜるとレビュー単位が崩れる。代わりに、今回作る互換層は将来の N246 がそのまま土台にできる置き方（パッケージ名・命名規則）にする（§2.1）。つまり「N246 の先行実施」ではなく「N246 と衝突しない最小互換層」を N251 の内側で作る。
3. **実施順序**: N251（26.x、3 バージョン・差分実測済み）→ その互換パターンを流用して N252（1.21.x、11 バージョン・未知の差分あり）。N150 は両方で使う検証プロジェクト生成スクリプトとして先に作る。N43 は本設計と同時に先行実施済み（別 PR）。
4. **リスクの所在**: 作業量の不確実性はほぼ N252 側にある。1.21.x は途中の機能ドロップ（1.21.2 / 1.21.4 / 1.21.6 / 1.21.9 等）で API が変わっている可能性が高く、検証で初めて差分が分かる。分割の判断基準は §4.3 に事前に定義する（検証しながら基準を動かさない）。

## 2. 共通アーキテクチャ（N251 / N252 共通）

### 2.1 パッケージ構成

単一 JAR の中身は 3 層に分ける。配置は将来の N246（PlatformBridge）が拡張しやすいよう、`compat` パッケージに寄せる。

```
com.pengin0503.itemmilestonelog
├─ （共通コード: 版に依存しない 34+ ファイル、そのまま）
├─ compat
│   ├─ McVersion.java          … 起動時に一度だけ版を判定する
│   ├─ TriggerCompat.java      … インターフェース（§2.2 A）
│   ├─ TagEventCompat.java     … インターフェース（§2.2 D）
│   ├─ ConfigCompat.java       … インターフェース（§2.2 E）
│   └─ client
│       └─ ScreenCompat.java   … インターフェース（§2.2 B/C、クライアント専用）
└─ compat.v26_1 / v26_2 / v26_3 / v121_1 / …  … 版別実装（系統ごとに必要なものだけ）
```

ルール:

- **共通コードは版別実装クラスを直接参照しない**。インターフェース経由でのみ触り、実装の選択は `McVersion` + 各 Compat の静的初期化（または ServiceLoader を使わない単純な switch）1 か所に集約する。
- **版別実装クラスは、その版でのみロードされる**。共通コード側のクラスが版別クラスへの参照をフィールド型・メソッド署名に含めると、そのクラスのロード時に参照解決が走る実装系があるため、参照はインターフェース型に限定し、具象クラス名は文字列リテラル＋反射、または版判定 switch の中だけに書く（switch の各分岐は実行されるまで対象クラスをロードしない通常の遅延解決に依存する。検証は §3.2 のバイトコード検査で行う）。
- 版判定は `net.minecraft.SharedConstants.getCurrentVersion().getName()`（または FML の `VersionInfo`）を起動時 1 回だけ読み、enum に正規化する。未知の版（例: 26.4）が来たら「最も近い下位の実装」を選んで警告ログを出す（フォールバック規則。26.4 対応の正式化は N150 の手順で検証してから範囲宣言を広げる）。

### 2.2 互換インターフェースの切り分け（26.x の 5 系統）

| 系統 | インターフェース | 版別実装 | 備考 |
|---|---|---|---|
| A トリガー | `TriggerCompat`: トリガーの登録と発火（`register(IEventBus)`, `trigger(ServerPlayer, TargetKey, boolean worldFirst)`） | v26_1 / v26_2 / v26_3 の 3 種。現行の `MilestoneRecordedTrigger` + `ModTriggers` を丸ごと版別側へ移す | 3 版すべて形が違うため共通化できる部分はない。実績のある現行コードをそのまま移すだけなので新規ロジックはゼロ |
| B/C クライアント画面 | `ScreenCompat`: 現在画面の取得、画面遷移、ホバー中スロット取得 | v26_1（旧 API）/ v26_2（gui 経由）/ v26_3（gui 経由＋getHoveredSlot）の 3 種。ただし B と C の境界がずれる（B は 26.2〜、C は 26.3〜）ため、実装は版ごとに 1 クラスにまとめ、メソッド単位でその版の正しい API を使う | クライアント専用パッケージに置き、サーバー側クラスから参照しない（現行の dist 分離を維持） |
| D タグイベント | `TagEventCompat`: `TagsUpdatedEvent` を受けて「静的データ再読込か」を返す | v26_1・v26_2（`getUpdateCause() == SERVER_DATA_LOAD`）/ v26_3（`shouldUpdateStaticData()`）の 2 種 | `Tracker.onTagsUpdated` 本体（TagIndex 再構築・警告）は共通側に残す |
| E Config | `ConfigCompat`: `registerConfig` の呼び出し | v26_1・v26_2（COMMON）/ v26_3（LOCAL）の 2 種 | 実装時に「26.3 で COMMON のままだと何が起きるか」を先に確認する。単なる改名なら意味差（同期・保存先）の有無を NeoForge の変更履歴で裏付ける |

- `versions/26.1.2` を **26.x 系の正プロジェクト**に改称する（ディレクトリ名は `versions/26.x` とし、`gradle.properties` の `minecraft_version` は基準版 26.1.2 のまま）。`versions/26.2` / `versions/26.3` の各プロジェクトは削除し、代わりに「検証専用プロジェクト」を §3.1 の手順で一時生成する（リポジトリには残さない、または `versions/verify/` 配下に生成して .gitignore する。N150 スクリプトの出力先として定義）。

- `check-identical-files.sh` は役割が変わる: 版別プロジェクト間の同一性チェックは不要になるが、**共通コードが版別 API を直接参照していないことの検査**に転用する（§3.2）。スクリプトの改修は N251 の一部として行う。
- JAR ファイル名: `itemmilestonelog-neoforge-26.x-<mod_version>.jar` / `itemmilestonelog-neoforge-1.21.x-<mod_version>.jar`（分割時は `1.21.1-1.21.4` のような範囲表記）。`verify-jar.sh` と `check-release.sh` のファイル名パターンを追随させる。

基準版プロジェクトの `gradle.properties` を変更する（値は実装時に NeoForge 側の実在バージョンで裏付ける）。

| 項目 | 26.x JAR | 1.21.x JAR |
|---|---|---|

## 3. N251（26.x 単一 JAR）詳細

### 3.1 バージョンごとの検証手順

正プロジェクト（基準 26.1.2）で JAR を 1 本ビルドし、その**同一 JAR** を各版で検証する。検証は 3 段階:

1. **単体テスト**: 基準版プロジェクトで従来どおり `test` を実行（共通コードのテストは版非依存）。版別実装クラスはコンパイル確認のみ各版プロジェクト側でも行う（§3.3 の検証プロジェクトで `compileJava`）。
2. **実サーバー検証**: 既存の `.github/scripts/run-server-tests.sh` を拡張し、「指定した MC / NeoForge の製品サーバーに、基準版でビルドした JAR を入れて起動・RCON・（対応版では）bot 参加・データ保存/再読込確認」を行う。現行スクリプトは `versions/<mc>/build/libs` の JAR を前提にしているため、対象 JAR のパスを引数で受け取れるようにする。
   - 26.1.2: min / latest の両 NeoForge（現行 CI と同じ）
   - 26.2: NeoForge 26.2.0.57（min）/ 26.2.0.95（latest）
   - 26.3: NeoForge 26.3.0.76（min）/ 26.3.0.115（latest）
3. **クライアント手動確認**: 実機クライアントでの GUI 確認（画面遷移・ホバーツールチップ等、B/C 系統の動作）は自動化できないため、1.2.0 の F41/F42/F44 と同様に pen の実機確認項目としてチェックリスト化する。対象は最低限「26.1.2 と 26.3 の両端」（中間の 26.2 は B が 26.3 と、C が 26.1.2 と同じ組み合わせではないため、可能なら 3 版とも）。

CI（`.github/workflows/main.yml`）への反映: 従来の「版ごとビルド」マトリクスは「正プロジェクトのビルド＋単体テスト」と「同一 JAR の各版サーバー検証」マトリクスに組み替える。NeoForm キャッシュのキー設計（版ごと 1 エントリ）はサーバー検証側が引き継ぐ。

### 3.2 バイトコード検査（新規）

単一 JAR 化の成否は「共通クラスが、ある版にしか存在しないバイナリ名を参照していないこと」で決まる。ソース上の分離（§2.1 のルール）を機械的に裏付けるため、マージド JAR に対してバイトコード検査を新設する。

- 対象: マージド JAR 内の `compat/v26_*` 配下以外の全クラス
- 方法: `javap -v` の定数プールに以下の禁止パターンが現れたら失敗とする
  - `net/minecraft/advancements/criterion/` 配下への参照（26.2 以降に存在しない）
  - `net/minecraft/advancements/triggers/`・`net/minecraft/advancements/predicates/` 配下への参照（基準版 26.1.2 に存在しない）
  - `TagsUpdatedEvent$UpdateCause` / `getUpdateCause`（26.3 で削除）
  - `Minecraft` のフィールド `screen` / メソッド `setScreen` への参照（26.2 で削除）
  - `AbstractContainerScreen#getSlotUnderMouse`（26.3 で改名）/ `getHoveredSlot`（26.1.2 に存在しない）
  - `ModConfig$Type` の版別定数（`LOCAL` 等）への共通クラスからの参照
- 実装: `.github/scripts/check-merged-jar-bytecode.sh`。CI のマージジョブと手元でのマージ時に実行する

### 3.3 単一 JAR のビルド（マージ方式。§2.3 の改訂）

実装段階で判明した制約により、§2.3 の「正プロジェクト一本化（26.2 / 26.3 プロジェクト削除）」は採らない。版別実装クラスは、その版にしか存在しないクラス（例: 26.2 の `advancements.triggers.*`）を参照するため、基準版のクラスパスではコンパイル自体ができない。版別クラスを版ごとにコンパイルする仕組みは既存の版別プロジェクトがそのまま担えるので、構成を次のように改める（本節が §2.3 に優先する）。

- 版別プロジェクト（`versions/26.1.2` / `26.2` / `26.3`）は存続し、「その版の版別クラスをコンパイルし、その版で単体テストとサーバー検証を行うハーネス」として使う。ディレクトリ改称（`versions/26.x`）は 1.3.0 では行わず、N246 に送る
- リリース JAR は **マージ** で組み立てる: `tools/merge-26x-jar.sh` が、基準版（26.1.2、最小 NeoForge）の JAR を土台に、26.2 / 26.3 の JAR から `compat/v26_2/**` / `compat/v26_3/**` のクラスだけを重ね、`META-INF/neoforge.mods.toml` の Minecraft 依存の `versionRange` を `[26.1.2,26.3]` に書き換えて、`itemmilestonelog-neoforge-26.x-<mod_version>.jar` を出力する
- マージの安全条件: 版別クラスはすべて版固有のパッケージ名（`compat.v26_*`）を持つため、クラス名の衝突は起きない。共通クラスは土台 JAR のものだけを使う（他版 JAR からは版別パッケージ以外を取り込まない）。マージスクリプトは「取り込む版別クラスの一覧が想定と一致すること」を検証し、想定外の差分があれば失敗させる
- 検証: `.github/scripts/verify-merged-jar.sh`（新規）が、3 版分の版別パッケージの存在、mods.toml の範囲、重複エントリの有無、§3.2 のバイトコード検査をまとめて確認する。CI にマージジョブを追加し、マージド JAR をアーティファクトとして残す

### 3.4 実装の段取り（N251）

0. N150（§5）: 検証プロジェクト生成スクリプト＋検証マトリクス
1. 互換レイヤー導入: インターフェースと版別実装を作り、呼び出し側をすべて互換経由に変える（版別プロジェクトは従来どおり各版でビルド・テスト）
2. トリガークラスの版別パッケージ移設（マージで同名衝突を避けるため）＋マージツールと CI マージジョブ

4. クライアント手動確認（§3.1 手順 3、pen の実機確認）

## 4. N252（1.21.x 単一 JAR）詳細

### 4.1 検証の進め方

- 対象: 1.21.1（基準、現行プロジェクト）を起点に 1.21.2 → 1.21.3 → … → 1.21.11 の順に 1 版ずつ検証する。あわせて 1.21（無印）も確認し、互換が取れれば範囲に含める
- 手順: N150 スクリプト（§5）で `versions/verify/<mc>` に検証プロジェクトを生成し、その版の NeoForge（最小版）で `compileJava` と `test` を通す。コンパイルが通らなければ差分を特定し、N251 と同じ流儀で互換クラス化できるかを判定する
- 記録: 結果（状態・NeoForge の実在バージョン・差分の要点）は `docs/VERSION_MATRIX.md` に版ごとに残す。NeoForge のバージョンは推測で書かず、公式プロジェクトページで実在を確認してから記入する
- 互換レイヤー: 1.21.x 側の版別パッケージは `compat.v121_*` とし、判定 enum とファクトリは 26.x と共通の仕組み（`McVersion` / `McCompat`）に 1.21.x の分岐を足す形で拡張する。世代（Java 21 / 25）が違うため 26.x と 1.21.x の JAR は分けたままにする

### 4.2 mods.toml の範囲

検証が全版で通れば `[1.21.1,1.21.11]`、1.21 無印も互換が取れれば `[1.21,1.21.11]`。NeoForge 範囲は `[21.1.1,)` のまま（§2.4）。

### 4.3 分割判断基準（先に固定する）

1.21.x を 1 本にまとめきれず 2 本に分けるのは、次のどちらかに該当した場合だけとする。該当しない差分は互換クラスで吸収し、安易に分割しない。

- (a) 差分のあるファイルの「核ロジック」自体を版で分岐させる必要がある（呼び出し箇所の隔離では済まない）
- (b) 1 つの区間の中で、新しい互換系統（インターフェース＋版別実装の組）が 2 つ以上必要になる

分割する場合は、非互換が入る版を境界にして前後で分け、根拠を `docs/VERSION_MATRIX.md` の該当行に記録する。

### 4.4 ビルド

26.x と同じマージ方式（§3.3）を 1.21.x 側にも適用する。土台は 1.21.1 の JAR、版別パッケージ（`compat.v121_*`）を各版の検証済み JAR から重ね、mods.toml の範囲を §4.2 の値に書き換える。

## 5. N150（新バージョン追加の支援）

- `tools/new-version-project.sh <mc> <neo_min> <neo_latest> [--from <base>] [--parchment-mc <ver>] [--parchment <ver>]`: 基準プロジェクトを `versions/verify/<mc>/` にコピーし（build / run / logs / .gradle は除外）、`gradle.properties` の版情報を書き換える。検証専用プロジェクトはリポジトリに残さない（`versions/verify/` は .gitignore 済み）
- `docs/VERSION_MATRIX.md`: 版ごとの検証状態と差分メモを管理する表。N251 / N252 の進行とともに更新する

## 6. 公開（publish）への影響

- リリースに `publish-manifest.json` を同梱し、「成果物ファイル → 対応ゲームバージョンのリスト」の対応を宣言する。`publish.yml` は JAR ファイル名からの版解析をやめ、マニフェストを読む
- 成果物数の前提は「4 本固定」から「2 本（1.21.x が分割された場合は 3 本）」に変わる。`check-release.sh` も追随させる
- Modrinth は 1 つの版エントリに複数 `game_versions` を付けられる。CurseForge も 1 ファイルに複数の MC バージョン ID を付けられる。冪等性（再実行時の重複判定）は「版の集合」の比較に変える
- 実装は N252 の最終段階（リリース準備）で行う。それまでは現行の 4 本前提の publish を触らない

## 7. 実装順序と体制

N150 → N251（§3.4）→ N252（§4）→ リリース準備（§6）の順。主担当は DSH（DeepSeek V4.1 Flash）、フォールバックは agy → Claude Code の順（pen の指定）。Gradle 実行・コミット・PR は司令塔（このチャット）が担い、各段階で GCE ビルド VM と GitHub Actions の両方で検証してから次へ進む。

## 8. リスク・未決事項・注記

- §2.1 は版判定に `SharedConstants.getCurrentVersion().getName()` と書いたが、26.x の実 API はレコード形式の `name()`（`getName()` は存在しない）。実装は `name()` を使う（実装時に実測で確認済み）
- 未知の将来版（26.4 等）が範囲外から読み込まれることは mods.toml の範囲宣言で防がれる。範囲内の想定外の版に対しては、`McVersion` が最も近い既知の版別実装を選び、正式対応は N150 の手順で検証してから範囲を広げる
- NeoForge 側の API 変動に備え、版別プロジェクトは従来どおり「最小版＋最新版」の 2 系統で CI ビルドを続ける（マージド JAR の土台は最小版）
- §2.3 の当初案（プロジェクト一本化・改称）を取り下げた経緯は §3.3 に記録した。一本化の是非は N246 で改めて扱う
